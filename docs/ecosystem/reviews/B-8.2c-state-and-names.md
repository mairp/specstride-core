# B-8.2c — Consistency: state paths, logical names and record schemas

Reviewer: independent agent. Date: 2026-09-29.

Scope: `spec.md`, `plan.md`, `tasks.md`, `data-model.md` and `contracts/` of the 40 features
`specs/101-*` to `specs/149-*` (368 files), checked against feature 100: `annexes/B-state.md`
(§B.3, §B.5 with 125 logical names, §B.6 to §B.20), `annexes/X-cross-layer.md` §X.8,
`contracts/data/layout.json`, `layout-old-side.json`, `identifiers.json`, `further-schema-ids.json`
and the 30 files of `contracts/schemas/`.

Method: Python scripts and `grep`, kept in the scratch directory `B-8.2c/`.

| Script | What it extracts |
|---|---|
| `names.py`, `names2.py` | Every token of the grammar of a logical name; compared with `layout.json` after the parameters are normalized; spelling of parameters compared exactly |
| `ctx.py`, `writers2.py` | Every line that holds a logical name or a record name together with a verb of writing or a root; read by hand (86 + 47 + 13 lines) |
| `schemas.py` | Every schema id (`specstride.*/n`, `specstride-*/vn`, `mol.*/n`) of the features, compared with the 83 ids found in feature 100; near misses by stem; `$id` of every schema file |
| `fields2.py` | Every field name in a line that names one of 16 records of feature 100, compared with the properties of the schema file |
| `paths` script | File names and roots of the `path` column of `layout.json` that the old side does not also hold, and the forms `$XDG_*`, `~/.config`, `.specstride/`, searched in every `spec.md` |
| identifier count | 37 spellings of the 11 identifiers, counted per feature |

Every finding below was read in the file at the line cited.

## Summary

| Severity | Count |
|---|---|
| critical | 0 |
| high | 3 |
| medium | 8 |
| low | 4 |

What holds: the logical names. Across 368 files no feature uses a name for state that annex B
§B.5 lacks, apart from one proposal in a queued question; the spelling of names and of their
parameters is the same everywhere; no `spec.md` requirement names a physical path of the new
product; the identifiers have one form; 151 field references in 17 features match the schemas
of feature 100; no schema file of a feature has an `$id` that collides with another.

The faults lie where a record crosses two features, and where feature 100 was amended after the
features were written.

The three most serious findings:

1. B-8.2c-001: the writer (109) and the reader (146) of the result of `harness verify` name four of its five fields differently.
2. B-8.2c-002: feature 105 has the engine write a fact into the run record, which the runtime root writes and whose schema has no field for the fact.
3. B-8.2c-003: the source inventory of feature 140 carries `schema_version` and no `schema` field, against F100-FR-227 and F100-FR-048.
